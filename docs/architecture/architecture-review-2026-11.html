现状体检

分层是骨架，真正的问题在层与层的接缝。下表按严重度排列—— P0 是「架构承诺与实现不符」，P1 是「结构性问题」，P2 是「工程债」。

值得保留的六项设计

Keep

依赖方向机器可证

四层单向依赖由 check_architecture.py 校验，0 violation。这比多数同规模项目做得好。

Keep

LLM 层抽象成熟

resolver.resolve_chat_llm() 是唯一配置入口，provider 元数据全在 providers.yaml，LLMSpec 冻结契约。新增 provider 零代码。

Keep

PageSnapshot 是范本

frozen dataclass + MappingProxyType 深只读；超预算页不丢弃而是回退磁盘——cache 而非 filter。一次 lint 每页只读一遍。

Keep

零代码插件机制

~/.llmwikify/skills/ 下的 SKILL.md / *.py 由 plugin_loader 自动发现。新增能力不需要改主仓库。

Keep

显式元数据命名空间

bus 事件用 _meta_* 前缀承载控制信号，不污染 payload。借鉴 nanobot 的做法，做对了。

Keep

表驱动扩展点

extractor 的 _EXTRACTOR_REGISTRY、lint 的 RULES 都是纯数据表驱动，加规则不需理解引擎内部。

P0 — 架构承诺与实现不符（4 项）

P0-01多套 Agent 循环并存 runner_v2.py · research_runner.py · base.py:283 · subagent_worker.py:81

同一套 ReAct 语义（PRECHECK→REASON→ACT→OBSERVE→FINALIZE）、同一套 hook 点、同一套事件，各写一遍。 runner_v2.py 与 subagent_worker.py 的文本解析 + 工具循环逻辑同构； harness/quality_gate.py 与 research/gates.py 各有一套质量门。

2026-11-02 实测更正：原判断「5 套」有误——apps/research/engine.py 是接线层不是循环； apps/chat/base.py::aask_with_tools 生产零调用者（事实死代码）。实为 4 处循环， 其中 runner_v2 与 research_runner 结构完全同源（后者 docstring 自陈 mirrors runner_v2）。

影响 任何 hook 语义变更、compact 策略、确认流程改动都要同步多处——这是最可能产生「改了 A 忘了 B」的根源。 → 方案 P1：收敛为单一 AgentRuntime + 声明式 Plan（已落地：research 与 chat 已迁移）。

P0-02存储抽象被 95 处直连 FS 击穿 kernel/storage/backend.py:9 · wiki/mixins/** · wiki.py:219,403

WikiBackend Protocol 声称「可换 in-memory / 远程」，但 mixin 层有 95 处直接 read_text / write_text / rglob；Protocol 真正被调用的只有 5 处。 wiki.py 自身也直连文件系统，backend.py:144 直接 new WikiIndex(db_path)。

影响 非 FS 后端目前不可实现——这是分层的形式化胜利掩盖下的实质失败。 → 方案 P2：引入 PageStore 端口，收敛直连 FS。

P0-03SSE 契约前后端漂移 apps/chat/agent/events.py:17-42 · ui/webui/src/api.ts:33-44

后端定义 17 种事件类型，前端 ChatStreamEvent union 只有 12 种。 session_init / user_message / compacted / command_done / phase 五类在前端没有对应类型。契约纯手工双写，无 codegen、无契约测试、CI 不校验。 另有重复定义：apps/chat/agent/unified/events.py:17 又抄了一份。

影响 前端只能靠 any 兜底，事件字段一改就静默失效。 → 方案 P4：契约即代码，单一 schema 源 + CI 校验。

P0-04apps.chat ↔ apps.research 包级循环依赖 apps/research/engine.py:16-30 ↔ apps/chat/gatherer.py:147

apps/research 反向 import apps.chat.agent.research_runner / gatherer / harness； 而 apps/chat/gatherer.py 与 skills/workflows/subagent_worker.py:727 又 import apps.research.web_search。apps/research/base.py 声称 research 是「base 的自然锚点」，但实际是双向的。

影响 同层循环是分层架构里最难拆的一类——它让「apps 可以自由组合」的前提失效。 → 方案 P5：抽取 apps/knowledge/ 共享内核，research 与 chat 均依赖它。

P1 — 结构性问题（5 项）

P1-01Orchestrator 是 God Object apps/chat/agent/orchestrator.py（1,016 行）

一个类同时承担：SSE 事件工厂（ChatEvent 12 个静态方法）、会话 CRUD、确认流、 斜杠命令路由、Runner 构建、持久化 Hook、工具注册表缓存。

→ 拆为 ChatService / SessionManager / CommandRouter / EventFactory / ToolRegistryCache。

P1-02双 Hook 体系 foundation/callback/composite.py:25（13 钩子） vs kernel/agent/hook.py:17（16 钩子）

两套语义重叠的 hook 点，桥接在 apps 层 unified/hook_adapter.py:21。 桥接层本身位于「生产代码零引用」的死目录里。

→ 统一到 foundation 的 16 钩子集，kernel/agent/hook.py 改为 re-export。

P1-03Lint 快照是隐式契约 kernel/wiki/lint/__init__.py:101,105

run_with_snapshot 用 type(self).run is not Rule.run 反射判断规则是否覆写—— 新规则作者不知这条隐藏协议，快照优化会静默失效（退回逐页读盘，计数门禁却仍绿）。

→ 引入显式 SnapshotRule 基类或 ClassVar[snapshot_capable] 声明。

P1-04进程内状态不可共享且泄漏 orchestrator.py:244-246

_session_status 仅在一处 pop；_tool_registries 只增不减，key 为 (session_id, wiki_id)——长跑进程内存泄漏。多实例部署时这些状态无法共享 （channels/websocket.py 注释自述「单 process」）。

→ 引入 Checkpointer 抽象，状态外置到 SQLite/Redis，进程内只做缓存。

P1-05Skill 白名单陷阱 apps/agent/tools/skill_adapter.py:43-51

SkillToolAdapter.exposed_skills 是硬编码白名单。注册了新 skill 但没加进这个列表 → LLM 永远调不到，且没有任何提示。这是「注册了却调不到」最常见的坑。

→ 默认全暴露 + 显式 opt-out 列表，或让 skill 自身声明 exposed: bool。

P2 — 工程债速览（8 项）

P2-01死代码

apps/chat/agent/unified/ 13 文件 / 1,119 LOC，生产零引用（仅测试引用）。 2026-11-02 更正：apps/chat/research_engine/ 不是死代码—— apps/chat/clarifier.py 与 apps/chat/harness/review.py 在用它。

P2-02CLI 双清单

commands/__init__.py 的 import 块与 register 块必须手工同步；注释写「27 commands」实际 33。 2026-11-02 更正：WikiCLI 不是意外双轨——它是有意的 backward-compat 公开 API （llmwikify/__init__.py 导出），已加显式弃用说明。

P2-03mypy 豁免 138 模块

含 interfaces 关键路径与整个 apps.chat。Command Protocol 签名与 33 个实现不一致（wiki_root: Path vs wiki: Any）——正因 Any 才没被捕获。

P2-04CI 覆盖缺口

addopts 默认 --ignore=tests/e2e；e2e.yml 跑的是 shell 脚本链而非 playwright 用例；WebUI 零 CI（无 npm/vitest/tsc）；check_architecture.py 未接入任何 workflow。

P2-05打包漏 UI

[tool.setuptools.package-data] 不含 ui/webui/dist，find_webui_dist() 只在源码树找得到 → pip install 后 serve --web 无界面。

P2-06发布链路断点

version-bump.yml 的 add-paths 指向不存在的 src/llmwikify/_version.py（真实位置 foundation/version.py）；all extras 漏了 llm（tiktoken）。

P2-07文档漂移

AGENTS.md 写 apps/chat/agent/runner.py（实为 runner_v2.py）；mixins 声称 WikiMeta metaclass（不存在，实为普通多继承）；kernel/__init__.py:19 仍宣称已删的 quant 子包。

P2-08质量门禁虚高

fail_under = 15，注释写「当前 16.27%（mock-only）」——实际全量已 80.3%。门禁设得极低，任何回退都不会被发现。importlinter contracts = [] 空配置。

业界的三条主线 —— llmwikify 缺什么

主线 A

单一运行时 + 声明式编排

LangGraph 用 Pregel 图、Temporal 用 Operator、K8s 用 reconcile 循环—— 执行引擎只有一份，差异用声明式配置表达。llmwikify 反其道：5 个引擎各写一遍。

收益：hook/compact/确认语义改动只需改一处；新增场景 = 写一份 Plan，不写一份引擎。

主线 B

状态外置 + 可持久化

LangGraph Checkpointer、Temporal 事件溯源、K8s etcd—— 运行状态与进程分离，才能水平扩容、崩溃恢复、断点续跑。 llmwikify 的会话状态在进程内 dict，且只增不减。

收益：多实例部署成为可能；长跑进程不再泄漏；崩溃可恢复。

主线 C

契约即代码 + 自动校验

K8s CRD、protobuf、OpenAPI codegen、Temporal 的 payload schema—— 契约是单一源，客户端由它生成。llmwikify 的 SSE 契约靠人手同步两份， 已经漂移出 5 种事件。

收益：前后端契约漂移在 CI 阶段就被拦下，而不是用户报「按钮不灵」。

llmwikify 的差异化优势：本地优先、零代码技能插件、完整的知识图谱与 lint 体系、 MCP 原生、多入口（CLI/MCP/HTTP/WS）。这些是 Dify/LangGraph 都不提供的。 需要补的不是功能，是把已有能力「声明化 + 契约化」—— 把 5 套循环收敛成 1 套 + 声明式 Plan，把手工双写的事件表变成单一 schema 源。
04

目标架构

目标态不推翻现有分层，而是把三处「层内复制」升级为「声明式配置」， 并把两处「契约手工同步」升级为「单一源 + 自动校验」。 四层结构保持不变——它是对的。

05

改进方案

八项方案，每项给出现状 → 目标的对照、迁移步骤与可验证的收益。 顺序即依赖顺序：P1 先行（收敛运行时），P2 承接（端口化），P4 收口（契约固化）。

1

收敛 Agent 运行时

P0-01
现状
5 个独立 ReAct 实现，各自的 hook 点、compact 策略、确认流程、事件语义。改一处漏三处。
→
目标
kernel/agent/runtime.py 单引擎 + Plan 声明式策略；Chat/Research/Subagent/Codegen 各写一份 Plan 配置，不写引擎。
  1. 提取 kernel/agent/runtime.py：把 runner_v2.py 的 5 步状态机原样搬入，行为零变化
  2. 定义 Plan Protocol：reasoner / actor / deciders / max_iterations / hooks / finalize 五个槽位
  3. ChatPlan 包装现有 ChatRunnerV2 行为；ResearchPlan 包装规则驱动 5 步；SubagentPlan 包装子进程 ReAct
  4. 把 research/engine.py 与 base.aask_with_tools 降级为 Plan 实现；删除 unified/ 目录
  5. 加计数门禁：任意 Plan 的 hook 触发序列必须与迁移前逐字相同（差分守卫）
收益 语义改动从 5 处降到 1 处；新增场景成本从「写 500 行引擎」降到「写 30 行 Plan」； 删除约 1,800 行重复代码。
2

存储端口化

P0-02
现状
WikiBackend Protocol 声称可换后端，但 mixin 有 95 处直连 read_text/write_text/rglob，Protocol 仅被调用 5 次。
→
目标
foundation/storage/page_store.py 定义 PageStore（read/write/list/stat）；LocalFileStore 与 InMemoryStore 两个 adapter；Wiki 全链路只经端口。
  1. 定义 PageStore Protocol：read_text / write_text / list_pages / stat / exists
  2. LocalFileStore 适配现有语义（含 UTF-8 强制、errors="replace" 降级）
  3. 按 mixin 逐个替换 95 处直连——按改动量升序，先叶子 mixin（query/link）后核心（io/page_io）
  4. 给 InMemoryStore 写实现，用它跑全量测试——测试不碰磁盘本身就是收益
  5. 把 check_architecture.py 加一条新规则：kernel/wiki/** 内禁止出现 Path.read_text 直接调用
收益 非 FS 后端（远程对象存储 / 内存）真正可实现；测试可完全无 IO，速度与稳定性双升； check_architecture.py 从此能守住端口不被再次击穿。
3

抽取共享内核

P0-04
现状
apps.research ↔ apps.chat 包级双向 import。同层循环让「apps 可自由组合」的前提失效。
→
目标
apps/knowledge/ 承载两者共用的采集/搜索/质量判定；chat 与 research 均单向依赖它，互不引用。
  1. 识别循环边：research→chat.research_runner / gatherer / harness 与 chat→research.web_search
  2. 把 gatherer、web_search、source summary 逻辑移入 apps/knowledge/
  3. research 的 rule-driven 5 步下沉到 apps/knowledge/pipeline/，chat 与 research 共用
  4. 两侧改为单向 import；在 check_architecture.py 加「同层包不得互相 import」规则
取舍 这是一次中等规模的重命名+移动，会产生较大的 diff。 建议在方案 1 完成后立即做——此时循环的语义边界已由 Plan 划清，搬迁更安全。
4

契约即代码

P0-03
现状
后端 17 种 SSE 事件 / 前端 12 种 union，纯手工双写，无 codegen、无契约测试、CI 不校验；unified/events.py 还抄了一份。
→
目标
后端维护唯一 events.schema.json；前端 ChatStreamEvent 由其生成；CI 有 contract job 拦截漂移。
  1. 把手写 events.py 常量改成从 events.schema.json 读取并校验（保持同名常量 API 不变）
  2. 写 scripts/gen_webui_types.py：schema → ui/webui/src/generated/events.ts
  3. 前端 api.ts 改为 export type ChatStreamEvent = GeneratedChatEvent，删掉手写 union
  4. CI 加 contract.yml：重新生成并 git diff --exit-code，漂移即红
  5. 删 unified/events.py 重复定义
收益 契约漂移从「用户报障」变成「CI 拦截」；新增事件类型只需改一处 JSON。 这也是本次评审中投入产出比最高的一项。
5

状态外置

P1-04
现状
会话状态在 orchestrator.py:244-246 的进程内 dict；_tool_registries 只增不减，长跑进程泄漏；多实例不可共享。
→
目标
SessionStateStore 抽象 + SQLite 实现（租约防多实例冲突）；进程内只做 LRU 缓存。崩溃可恢复，水平扩容解锁。
  1. 定义 SessionStateStore Protocol：get / set / clear / list_all
  2. SqliteSessionStateStore 存到既有 chat_sessions.metadata blob（session_state 键，无需加列）
  3. 把 _session_status / _abort_events 迁入；进程内 dict 改为 LRU 缓存（带 TTL 与上限）
  4. _tool_registries 改为按 wiki_id 缓存 + 引用计数或 TTL，修复泄漏
  5. 补一个「重启后可恢复会话」的集成测试
取舍 SQLite 写入会给每次会话操作带来 I/O。 建议状态写后异步落盘、读时按需回填内存，保持热路径无感。

显式能力声明

P1-03 / P1-05
现状
lint 快照靠 type(self).run is not Rule.run 反射判断；skill 暴露靠硬编码白名单。两者都是「不写对就静默失效」。
→
目标
规则与技能自带能力标记；框架只读标记，不猜。新增能力不写对会立刻报错而不是静默退化。
  1. Rule 加 snapshot_capable: ClassVar[bool] = False，删反射判断
  2. 新增 SnapshotRule(Rule) 子类，模板方法强制实现 detect_from_snapshot
  3. 加规则时若未声明快照能力，计数门禁报错而非静默通过
  4. Skill 加 exposed: bool = True 默认值；删除 exposed_skills 白名单
  5. 保留一份显式 hidden_skills 排除列表（用于内部技能）
收益 消除两类「注册了却调不到」的静默故障；新贡献者的第一课从「读源码找隐藏协议」变成「看一个类字段」。

拆分 God Object

P1-01
现状
orchestrator.py 1,016 行承担 6 类职责；apps/chat 单包 33.5k LOC / 169 文件；44 个 >500 行文件。
→
目标
ChatService（门面）/ SessionManager / CommandRouter / EventFactory / ToolRegistryCache 五个单一职责模块；每个子包 < 8k LOC。

演进路线图

三阶段推进。原则：先立契约，再动结构；先有门禁，再做重构。 每阶段结束时代码库必须比开始时更绿（测试数增加、门禁提高、违规数减少）。

Phase 1止血 + 固契约

把承诺兑现

消除 4 个 P0 中的 3 个，建立 CI 门禁基线

  • 契约即代码（方案 4）— 前后端 SSE 单一源 + CI 校验
  • 显式能力声明（方案 6）— lint 快照 + skill 暴露
  • CI 门禁（方案 8 前半）— 架构校验接入 / WebUI CI / fail_under=80
  • 死代码清理 — unified/（13 文件，生产零引用）；WikiCLI 标注弃用
  • 发布链路修复 — webui dist 打包 / version-bump 路径 / all extras

出口条件：CI 全绿 · 契约漂移可拦截 · 覆盖率 ≥80% 门禁生效

Phase 2结构收敛

把重复变成声明

单一 Agent 运行时 + 消除同层循环

  • 收敛 Agent 运行时（方案 1）— 5 套循环 → 1 套 + 4 份 Plan
  • 抽取共享内核（方案 3）— apps/knowledge/，解除 chat↔research 循环
  • 状态外置（方案 5）— SessionStateStore + SQLite 租约（已落地）
  • 钩子统一到 foundation 16 点，删除桥接层
  • 新增「同层包不得互相 import」架构规则

出口条件：循环实现仅 1 套 · 同层零循环 · 会话可跨进程恢复

Phase 3纵深优化

把端口做实

存储端口化 + 模块物理拆分 + 性能收尾

  • 存储端口化（方案 2）— 95 处直连收敛，InMemoryStore 落地
  • 拆分 God Object（方案 7）— Orchestrator 五分，chat 三包化
  • 类型门禁收敛 — foundation 严格化，mypy 豁免逐层递减
  • 性能：LLM 响应缓存、索引增量更新、工具 lazy import
  • 可观测性：接 OpenTelemetry（现有 llm_metrics 为基础）

出口条件：零直连 FS · 子包 <8k LOC · 可插拔存储后端

收益预期

维度当前Phase 3 后量级
改一处语义的改动点5 处（5 套循环）1 处（单一运行时）−80%
新增 Agent 场景成本~500 行引擎~30 行 Plan−94%
存储后端可选性仅本地 FSFS / 内存 / 远程解锁
契约漂移发现时机用户报障CI 拦截提前一个发布周期
横向扩容能力单进程多实例（状态外置）解锁
死代码~24 文件 / ~2,000 行0−2,000 行
类型覆盖138 模块豁免foundation 100% / kernel 80%+门禁可逐步加严
07

风险与取舍

架构改造的失败模式通常不是技术难度，而是范围失控与回归 undetected。以下为已识别风险。

风险

大重构与覆盖率提升抢带宽

当前 80.3% 覆盖、目标 95%，补测试本身需要大量时间。 若同时推进大规模搬迁，两者会互相挤压。

对策：先做「不改变行为」的项（契约、门禁、死代码）， 再做结构搬迁；每个结构 commit 必须补差分守卫测试。

风险

「收敛」误伤扩展性

5 套循环看起来冗余，但它们服务于不同场景（LLM 驱动 / 规则驱动 / 子进程）。 强行合并成一个僵硬的引擎会让新场景无处安放。

对策：统一的是执行骨架，不是场景语义—— Plan 允许自定义 reasoner/actor/decider，差异留在 Plan 而非引擎。

风险

端口化改造的回归面

替换 95 处直连 FS 是典型的「大量小改动」—— 每一处都可能引入编码、路径、错误处理的细微差异。

对策：InMemoryStore 与 LocalFileStore 跑同一套测试，行为差异必须为零；按改动量升序迁移，每步一个 commit。

风险

单人多线并行的上下文损耗

项目已在用多 agent 协作协议（docs/designs/refactor-*）， 但并行改动同一层文件会产生合并冲突（此前 P4/P4b 的 lint 改动就曾与他人并行）。

对策：按层分工（一人一层）， 跨层改动走 handoff 文档；每个 agent 的产出必须带可运行的回归测试。

总体判断：当前架构的骨架是对的——四层单向依赖、机器校验、插件机制、 快照式性能优化，都是高于同规模项目平均水准的设计。问题集中在层的接缝处： 抽象被绕过、语义被复制、契约被手工同步。这三件事恰好也是业界共识中最该自动化掉的部分。 不必推倒重来——按 8 个方案分三阶段收敛，同一份代码库可以做到既干净又不失现有能力。
