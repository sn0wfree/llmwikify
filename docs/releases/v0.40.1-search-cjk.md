# v0.40.1 — Search CJK Recall Fix

**Release date:** 2026-07-07
**Branch:** `dev/refocus-v0.40-2026-07-05`
**Scope:** Backend FTS5 tokenizer + LIKE fallback expansion
**Backwards compatible:** Yes (auto-migration on first server start)

---

## What's in this release

v0.40.1 fixes the **CJK search recall problem**: short Chinese queries
(2-3 characters like `配置`, `中文`, `算法`) returned **zero results** even when
many pages contained those terms.

### Why it was broken

SQLite FTS5's built-in tokenizers (`ascii`, `unicode61`, `porter wrapper`)
all treat **contiguous CJK text as a single token**. The string
`从风格到配置` is indexed as ONE token, so querying for `配置` finds nothing.
The `porter` stemmer also adds English-specific noise without helping CJK.

### What this release does

1. **Drops `porter`** → small English-side regression in stemming, big win in
   schema clarity (CJK content no longer hides behind English stemming rules).
2. **Adds explicit `categories 'L* N* Co Mn'`** → helps with mixed Chinese+English
   content like `机器学习 algorithm` (separates at script boundaries).
3. **Expands the LIKE fallback** → when FTS5 MATCH returns 0 rows (regardless
   of reason), the search transparently retries with `LIKE '%query%'`. **This
   is what actually rescues short Chinese queries** — the FTS5 tokenizer
   change is the schema hygiene, but the LIKE fallback is the recall fix.
4. **Auto-migration** → existing wikis with the legacy tokenizer are upgraded
   transparently on first server start.

### Caveat

SQLite FTS5 has **no built-in CJK word-segmentation tokenizer**. Even with the
new schema, `MATCH '配置'` on a pure-CJK document returns 0 rows because the
indexed token is `从风格到配置` (or whatever contiguous CJK string was indexed).
The LIKE fallback catches this case but returns score=0 (no BM25 ranking).

For users who need true CJK BM25 ranking, the only solutions are:
- **External tokenizer** (jieba, hanlp) — adds a dependency we want to avoid
- **SQLite `trigram` tokenizer** — requires queries ≥ 3 chars; still imperfect
- **External search engine** (Meilisearch, Elasticsearch + IK) — architecture-heavy

For this release, we chose the pragmatic LIKE-fallback path. If CJK search
quality becomes a recurring pain point, `trigram` migration is a follow-up.

## Before / After

### Before (`tokenize='porter unicode61'`)

```bash
$ curl "http://localhost:8765/api/wiki/search?q=配置"
[]
# 0 hits — even though 42 pages contain "配置"

$ curl "http://localhost:8765/api/wiki/search?q=risk"
[
  {"page_name": "risk/Risk Parity", "score": 1.24, ...},
  ...
]
# English works fine, but uses porter stemmer (noise on edge cases)
```

### After (`tokenize='unicode61 categories "L* N* Co Mn" tokenchars "_"'`)

```bash
$ curl "http://localhost:8765/api/wiki/search?q=配置"
[
  {"page_name": "log", "score": 0, "snippet": "...", "mode": "fts5-zero-fallback"},
  {"page_name": "strategies/...", "score": 0, "snippet": "...", "mode": "fts5-zero-fallback"},
  ...
]
# Hits! But score=0 because the result came from LIKE fallback, not FTS5 BM25.
# This is the trade-off — recall improves, ranking accuracy is unranked.

$ curl "http://localhost:8765/api/wiki/search?q=risk"
[
  {"page_name": "risk/Risk Parity", "score": 1.24, "mode": "fts5"},
  ...
]
# English queries unaffected.
```

## Migration

### Automatic (recommended)

Just restart the server. `WikiIndex.initialize()` detects the legacy tokenizer
(`porter unicode61` in `pages_fts` schema) and rebuilds the index from the
`pages` metadata table on first connection. The rebuild tries to refill
content from disk:

- Tries `db_path.parent / <file_path>` (root level)
- Tries `db_path.parent / "wiki" / <file_path>` (standard `wiki/` subdir)
- Tries `db_path.parent / "raw" / <file_path>` (alternate `raw/` subdir)
- Pages whose files are still missing get a log warning; they refill on the
  next `upsert_page()` call or by running `llmwikify build-index` manually.

### Manual verification

```python
import sqlite3
from pathlib import Path

db = sqlite3.connect(Path.home() / ".llmwikify" / "index.db")
sql = db.execute(
    "SELECT sql FROM sqlite_master WHERE type='table' AND name='pages_fts'"
).fetchone()[0]
assert "categories" in sql, f"Still on legacy tokenizer: {sql}"
print("OK — new tokenizer active")
```

### Index rebuild CLI (if auto-migration misbehaves)

```bash
llmwikify build-index
# Existing CLI — rebuilds pages_fts from .md files on disk
```

## Technical Notes

### Tokenizer choice rationale

SQLite FTS5 supports several tokenizers:

| Tokenizer | CJK behavior | English | Verdict |
|-----------|--------------|---------|---------|
| `porter unicode61` | ❌ single token (whole phrase) | ✅ + stemming | Old default |
| `unicode61` (no categories) | ❌ same | ✅ | No improvement |
| `unicode61 categories 'L* N* Co Mn' tokenchars '_'` | ⚠️ contiguous CJK still single token, but mixed script splits | ✅ | **New default** |
| `trigram` | ✅ for queries ≥ 3 chars | ✅ substring | Future option |
| Custom (jieba, etc.) | ✅✅ word-segmented | ✅ | Heavy dependency |

The new schema picks the best built-in option that doesn't add dependencies.
It's a step forward but not a silver bullet for CJK.

### `LIKE` fallback semantics

Previously, the fallback to `LIKE '%query%'` only triggered on
`sqlite3.OperationalError` (FTS5 syntax errors). After this change:

1. Run FTS5 MATCH → got N rows
2. If N == 0 → run `LIKE '%query%' content` → return those results (unranked)
3. If FTS5 syntax error → also LIKE (existing behavior preserved)

The fallback is a single indexed scan on `pages_fts.content`, so the cost
is negligible for the empty-results case (the rare path). Snippets are
truncated to 200 chars (vs FTS5's 32-token snippet window).

### Performance

- **FTS5 size**: roughly the same for English wikis; slight decrease (no porter).
- **Search latency**: unchanged for typical queries.
- **Build index**: roughly the same speed.
- **LIKE fallback cost**: one extra indexed query only when FTS5 returns 0.

## Compatibility

- **API**: No breaking changes — `GET /api/wiki/search` accepts the same params.
- **MCP tools**: `wiki_search()` unchanged.
- **CLI**: `llmwikify search` unchanged.
- **Config**: New optional `search.tokenize` field; default = new schema.
- **Downgrade**: Reverting to v0.40.0 requires running `llmwikify build-index`
  after downgrade to rebuild with the legacy tokenizer.
